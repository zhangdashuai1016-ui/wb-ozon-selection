## 1. 这一轮解决什么

### 1.1 起因：r69 部署后主人点了按钮，软件停在「结果未知」

主人 2026-09-24 点了「对账并登记本轮导入」。**恢复动作本身成功**：作业从

### 1.2 但暴露出两个真问题

**问题一：判定完全不看错误级别**（`ozon-seller-api-de-adapter.mjs` 原 458 行）
```js
else if (status !== "failed" && item.errors.length > 0) gapCode = "import_task_errors_present";
```

## 3. 四项改动

### 3.1 ① 错误明细落盘并显示

按官方合同 `v1ItemError` 逐条规范化：`code / message / state / level / field / attributeId / attributeName`。
逐项限长、最多 50 条、**不落原始响应整包**、不落任何凭据。`errorCount` 保留，并要求**条数与明细数相等**。

**结构证据**：`docs/contracts/ozon-de-20260908/official-de-structural-openapi.json`
（`sourceUrl` = Ozon 官方 swagger，`originalAcquiredAt` 2026-09-08）：
```
GetImportProductsInfoResponseResultItem.errors : array of v1ItemError
v1ItemError = { code, message, state, level, field, attribute_id, attribute_name }
```

### 3.2 ② 按级别分类

```
level === 'ERROR_LEVEL_WARNING'  → 警告
其余一切（ERROR / INTERNAL / UNSPECIFIED / 空 / 任何不认识的串） → **按错误处理**
```
`imported` 且全为警告 → 按 `imported` 走；有任一非警告 → 维持 `unknown_outcome`；`failed` → `platform_failed`。

**级别枚举的证据与其边界**：同一份合同里有
```
ErrorErrorLevel = enum [ERROR_LEVEL_UNSPECIFIED, ERROR_LEVEL_ERROR, ERROR_LEVEL_WARNING, ERROR_LEVEL_INTERNAL]
```
**但它只被 `GetProductInfoListResponseError`（`/v3/product/info/list`）引用；
import/info 的 `v1ItemError.level` 在合同里是裸 `string`，没有 `$ref`、没有 enum。**
「两边同一套词」很可能为真，合同没有明文——**所以未识别一律从严**。
最坏结果 = 2026-09-24 当天的行为（停下来留证），**不会误放行**。
③ 跑出的真实样本用于事后校准，样本脱敏留档。

判定**只此一份**：`lib/ozon-import-error-level.mjs`（零 `node:` 依赖），适配器与观察合同共用。
（合同层原本独立绑了「非失败档 errorCount 必须为 0」，若只改一处，两边就会各写各的——r69 预览与适配器各拼标签值的教训。）

### 3.3 ③ 「按新分类重新观察一次」

主人显式点击，绑定同一 task / productId / 授权，**幂等一次**，**零外部请求、零平台写入**，
不重发导入、不生成生产记录、不改授权。真正的只读查询由观察作业按策略执行。

按钮**四条门槛缺一不亮**：停在 `unknown_outcome` + 观察记录已有 `product_id` +
策略有效 + **剩余预算**（`maxQueries − queryCount`）盖得住剩余查询。
挡住时逐档给理由：`ALREADY_REOBSERVED` / `NO_PLATFORM_PRODUCT` / `QUERY_BUDGET_EXHAUSTED` / `OBSERVATION_POLICY_UNAVAILABLE`。

> **③ 不是一点就通的承诺。** 若那 2 条确实含真错误，它仍会停在 `unknown_outcome`——
> 但这一次错误明细会整份落盘并在页面逐条显示。**先留证，其次才是往下走。**

### 3.4 ④ 店铺级默认观察策略

`SELECTION_REVIEW_D_PLATFORM_OBSERVATION_JSON` 新增**可选** `defaults`，按
「`productionBindingId` + `productionConfigurationVersion`」匹配，不钉候选与 SKU。
解析顺序：**逐品优先 → 店铺级默认 → 都没有才 null**。

**这解掉 r69 卡 3.3 记的那笔账**：今后新品不必先改 plist、重启服务才能上架。

## 7. 踩坑留痕（给下一个接手的人）

1. **改字段表之前先想旧落盘**：我一开始把 `errors` 加进 checkpoint 的**必填**字段表，
   而 `d-production-job-cursor.mjs` 那里是 `Object.keys().length === 字段数 + 2` 的**精确计数**——
   **这一改之前落盘的所有 `import_result_observed` checkpoint 都会被判成损坏**。
   改成可选：必填项照旧全查、仍不许出现表外键，只允许旧记录缺这一项。schema 同样从 `required` 移出。
2. **同一条规则不许有两份**：合同层独立绑了「非失败档 errorCount 必须为 0」，
   若只放宽适配器，两边就各写各的。抽成 `lib/ozon-import-error-level.mjs` 共用——
   r69 预览与适配器各拼标签值，害得主人看到的和实际发出的不一样，同一课不上第二遍。
3. **归档只留指针，不复制正文**：我把整份错误明细复制进 ③ 的归档，被实体归一化拒了
   （`PRODUCTION_ENTITY_JSON_INVALID`）。改法不是绕过校验，而是**本来就不该复制**——
   明细留在 `observationHistory`（追加、不被覆盖），归档只留 `priorObservationJobId` +
   指纹 + 条数 + 旧判定。与 r67 归档嵌实体正文同一课。
4. **回读要读对地方**：r69 部署回读时我从 `/api/state` 取 `runtime.softwareJobs`，读出「0 条 D 作业」。
   **那是 UI 投影，根本不含该字段。**数据 sha 没变才没让我据此下结论。
   业务事实要从数据文件或专用接口读，不能拿 UI 投影当权威。
5. **改错文件的静默失败**：我按「标签模块那行 import」当锚点去改 DE 适配器，
   可那行在**生产适配器**里——替换静默无效，跑出 `ReferenceError`，一次红 10 条。

6. **反向断言不能乱抓**：我一度拿整个 `dSoftwareExecution` 去搜 `items`/`offer_id`/`result`，
   这些**本来就合法存在**（冻结的导入请求体就是 Ozon 格式、`kind` 里就含 `result`）。
   已收窄到观察结果本身、改成键集合逐字比对。**"看起来很严其实在乱抓"的断言比没有断言更糟。**
7. **序号要接着数**：③ 照抄 r69 用了 `queryIndex: 1`，但那不是本轮第一次观察，
   撞 `SEQUENCE_CONFLICT`。改成 `queryCount + 1`——**且预算照常扣，重新观察不是免费重来。**
