## 一、先说最重要的结论

这14项不能统称为“废代码”或“孤儿代码”。它们实际混合了七类东西：

1. 当前服务仍在依赖的历史兼容底座；
2. 已经与业务数据隔离、但仍有独立 UI 的模拟沙盒；
3. 一部分已经隔离、一部分仍有条件调用的混合模块；
4. 只服务开发、打包、启动和部署的工程工具；
5. 能执行某些 D/E 动作、但尚未组成正式生产闭环的候选零件；
6. 没有正式调用方、但人工误运行仍可能改数据的高风险旧入口；
7. 已接当前源码 UI、却没有读取统一能力总账的地图草稿。

本轮发现三处不能照抄能力注册表标签的事实：

- 9.4 不是一整块旧 FireTrain。real-c1-preparation.mjs 是旧专用实现；lifecycle-c-stage.mjs 则包含通用 C1→C2 领域函数，并被当前服务的默认关闭兼容路由引用。
- 9.10 已经接入当前主源码的“全店能力地图”入口，但它独立维护14个静态节点，没有读取49节点能力注册表、14项待归位或8组重复比较组。
- 9.14 的标题写着“B利润与C1交接”，实际文件只创建 SKU 生命周期包并计算 B 利润；它没有创建 C1 交接。

还有一条全局证据警告：

- 冻结能力快照的结构和覆盖清单仍完整，但当前源码摘要已经与 2026-08-27 冻结摘要不同。本轮能力注册表测试有3项通过、1项因为源码摘要漂移失败。因此，冻结快照可以继续说明“当时三处副本里有哪些文件”，不能继续证明“当前源码已经重新验证”。

## 二、本报告怎样区分事实

下面每一项都把四层证据分开，避免把“看见文件”误说成“业务完成”。

| 证据层 | 它能证明什么 | 它不能证明什么 |
|---|---|---|
| 文件存在 | 仓库或快照里有这份源码 | 有人调用、UI可用、业务跑通 |
| 存在调用 | 当前源码中能找到明确导入、函数调用或路由 | 默认开关已开启、运行副本正在执行、平台成功 |

# 五、14项待归位能力逐项档案

## 9.1 历史候选分派地图

**所属小组：甲｜历史候选、旧协作与状态桥接**

### 一句话结论

它不是现在要建设的“全店能力地图”，而是旧时代给候选商品分配 M01—M12 工作节点、负责人、留言和恢复目标的调度地图。旧 UI 已被替换，但当前服务仍大量读取它，所以它不是孤儿，也没有真正完成隔离。

### 当初为什么开发

旧流程把一个候选交给不同 Codex 任务处理，需要知道：

- 商品当前落在哪个 M 节点；
- 应该交给“选品任务”还是“上架任务”；
- 是否已有派发在等待或运行；
- 失败后恢复到哪里；
- 历史留言属于哪个节点。

它像一张“车间排班板”。这张板管的是候选派工，不是代码能力健康。

### 表面看起来与实际能力

| 角度 | 结论 |
|---|---|
| 表面看起来 | 一张工作流地图，好像与“全店能力地图”是同一种东西 |
| 实际能做 | 读取旧 workflow-map.json；计算旧候选所在节点；查找活动派发；决定旧负责人；生成旧地图视图；支持历史留言、派发和恢复路由 |
| 实际不能做 | 不能说明代码模块健康；不能证明 A→E；不能作为统一能力注册表；不能决定模块接线；不能在当前规则下给正常 SKU 派 Codex |

### 输入 → 内部处理 → 输出

| 输入 | 内部处理 | 输出 |
|---|---|---|
| 旧 M01—M12 地图配置 | 读取节点与负责人 | 节点清单和负责人路由 |
| 候选旧 workflowStatus、processing、dispatches | 找到当前节点和活动派发 | activeDispatch、latestDispatch、恢复目标 |
| 旧留言 | 绑定候选或全局节点 | 历史评论视图 |

### 谁依赖它，它依赖谁

- 当前调用方：server.mjs 仍导入 readWorkflowMap、activeDispatchForCandidate、validateNodeExecution 等函数。
- 当前影响：多个 A、采集、确认、C、生产相关路由会先检查“旧活动派发是否存在”，所以它仍能挡住当前请求。
- 历史调用方：旧 Workflow Map UI、旧 Codex 派发、恢复和留言功能。
- 当前 UI：WorkflowMap.jsx 现在只是 ThreeStoreMap 的兼容别名；当前 App 没有继续加载旧地图页面，但候选详情仍可能显示旧派发字段。
- 它依赖：data/workflow-map.json、候选旧状态和 dispatch 数据。

### 孤立程度

**仍被依赖，属于“前端页面已替换、后端核心兼容仍在”的部分游离状态。**
不能叫纯孤儿。更不能只删文件，因为 activeDispatchForCandidate 仍在大量当前路由中起互斥作用。

### 与当前架构的关系

- A→E：没有正常主线资格，只能保存历史兼容信息。
- Codex Independence：旧地图与旧派发高耦合；如果继续给正常 SKU 派 Codex，就直接违反最高不变量。
- 全店经营工作台：只应展示必要历史事实，不应继续以旧地图组织正常业务。
- 全店能力地图：应把它作为“历史兼容能力”展示，不能拿它自己当能力地图底座。

### 与其他待归位能力的关系

- 与 9.2 高度互补：9.1 决定旧节点和负责人，9.2 真正尝试创建 Codex 轮次。
- 与 9.9 相互依赖：旧扁平状态是地图判断候选位置的重要输入。
- 与 9.10 名字像、职责完全不同：9.1 管候选派工，9.10 管代码能力说明。

### 已确认的老板决定

9.1 将来进入全项目统一、公开可查的隔离区：

- 完整保留历史读取；
- 禁止参与新的 A→E；
- 禁止产生新的 Codex 分派；
- 所有 Agent 都能按固定编号发现；
- 展示来源、原位置、隔离原因和依赖；
- 默认只读，不得偷偷接回主线；
- 恢复、合并或退役必须由主人重新授权。

**本轮只记录决定，没有修改路由、数据、注册表或 UI。当前源码还没有完全实现这项隔离决定。**

### 未来三种处理的主要风险

- 接入主线：会让旧 M 节点重新支配 A→E，并可能恢复正常 Codex 派发，风险最高。
- 暂时保留：必须继续承受历史数据与当前路由耦合，但最利于安全迁移。
- 退役：如果先删后拆，会破坏当前活动派发互斥、历史留言和恢复读取。

### 调查建议

按老板已决定的方向，未来先做“可发现的只读隔离”，再逐路由拆掉写入和正常派发能力；不要先删文件。本轮不实施。

## 9.2 旧 Codex 分派与协作路线

**所属小组：甲｜历史候选、旧协作与状态桥接**

### 一句话结论

这套代码真的具备“把候选资料整理成提示并向 Codex App Server 发起任务轮次”的能力。当前主源码仍保留路由和调用，但自动投递只有显式开启环境开关才创建；当前运行副本是否开启，证据未知。它绝不能回到正常 SKU 主线。

### 当初为什么开发

过去软件自己不能完成全部选品与上架工作，于是把候选交给“选品任务”或“上架任务”，等待 Codex 做完再把结果写回。它相当于旧车间里的“人工派单员”。

### 表面看起来与实际能力

| 角度 | 结论 |
|---|---|
| 表面看起来 | 一个普通任务分派工具 |
| 实际能做 | 清洗候选快照；根据节点附加技能和提示；检查目标任务忙闲；发起 Codex turn；接收运行编号；处理写锁、审批、完成和失败 |
| 实际不能做 | 不能作为正常 A→E 发动机；不能替代软件状态机；不能把“任务已启动”当业务完成；不能在没有维护授权时处理正常 SKU |

### 输入 → 内部处理 → 输出

| 输入 | 内部处理 | 输出 |
|---|---|---|
| dispatch、候选、节点、负责人 route | 删除敏感查询参数并生成候选快照 | 结构化任务提示 |
| 负责人任务状态 | 判断空闲、忙碌或写锁 | 等待、阻塞或允许启动 |
| Codex App Server 返回 | 校验真实 turnId | 运行中、等待或明确失败 |

### 谁依赖它，它依赖谁

- 当前调用方：server.mjs 仍实例化 CodexDispatcher，并保留候选派发、继续、认领、进展、完成、审批和恢复路由。
- 当前门禁：SELECTION_REVIEW_AUTO_DELIVER 必须显式为 on/true，且 CODEX_OFFLINE 不能开启，才创建 dispatcher。
- 当前 UI：src/api.js 仍有 dispatchCandidate 方法；当前组件未找到直接派发按钮，旧派发状态仍在候选视图中出现。
- 历史调用方：9.1 的节点负责人路由、旧候选恢复、旧 A/B/C 派发。
- 它依赖：本机 Codex任务服务、route/threadId、旧 dispatch 数据。

### 孤立程度

**不是孤儿；属于“代码和后端路由仍在，正常自动投递默认关闭，业务资格已被新规则否定”的高风险历史支路。**

### 与当前架构的关系

- A→E：正常商品禁止进入。
- Codex Independence：只能考虑用于已持久化 ExceptionCase 的开发维护，而且必须先有真实维护轮次编号，不能用它代替主人确认或平台调用。
- 全店经营工作台：只能显示“历史派发”或“真正异常维护”，不能显示正常商品“Codex处理中”。
- 全店能力地图：应把它画成异常支路或历史隔离，不是主线节点。

### 与其他待归位能力的关系

- 与 9.1 高耦合，不是简单重复。
- 与 9.12 中的旧派发迁移脚本有关：那些脚本能重新排队旧 Codex 状态。
- 与正式 ExceptionCase 有表面相似，但当前 dispatcher 还保留大量旧候选语义，不能直接等同。

### 未来三种处理的主要风险

- 接入主线：违反 Codex Independence，可能造成状态只存在于会话、重复执行和无法判定卡点。
- 保留为异常维护：需要把候选派发语义收窄到 ExceptionCase、revision、job 和一次维护授权。
- 退役：要先保留历史 turnId、失败和审计读取，否则会丢失旧任务追溯。

### 调查建议

先证明正常生产路径完全不可达，再判断哪些底层“创建维护轮次”能力可复用；不要把整个旧 dispatcher 原封不动升级为异常系统。本轮不选择。

## 9.3 第2A模拟验收

**所属小组：丙｜纯模拟沙盒**

### 一句话结论

它是一套真正可操作的演示页，但所有商品、证据、时间和结果都是固定模拟数据。它可以说明“规则函数怎样工作”，不能说明真实候选、真实费用或真实 A→B→C1 已经走通。

### 当初为什么开发

当真实数据、外部证据和运行链还没准备好时，需要一张不会污染共享候选的演示卡，验证：

- 主人如何在一张卡确认或淘汰；
- 缺成本、重量、尺寸时怎样停在 A；
- B 通过后怎样只创建一次 C1 交接；
- 技术失败怎样不改业务结论。

它像“驾校模拟器”：能练操作，不能拿模拟里程当真实运输记录。

### 表面看起来与实际能力

| 角度 | 结论 |
|---|---|
| 表面看起来 | 一条已经跑通的 A→B→C1 |
| 实际能做 | 用固定 fixture 在内存中验证 A 卡、B 利润、C1 交接、幂等和失败隔离 |
| 实际不能做 | 不读真实候选；不保存共享数据；不访问 Ozon/WB/1688；不创建真实任务；不产生真实利润或上架资料 |

## 9.5 分阶段构建与部署边界

**所属小组：丁｜构建、启动、部署与历史数据工具**

### 一句话结论

它们是给开发者打“小阶段发布包”的工程工具：锁定允许复制哪些文件、禁止夹带哪些模块、检查旧摘要并生成清单。它们不推进任何商品，也没有进入 package.json 的正式 build/start 命令。

- 允许文件清单；
- 运行副本与目标源码摘要；
- 允许/禁止差异标记；
- 构建包和 manifest。

它像每次搬家都单独写一张装箱单。装箱单能防止拿错箱子，但不等于新房已经入住验收。

## 9.6 本机启动与运行副本部署脚本

**所属小组：丁｜构建、启动、部署与历史数据工具**

### 一句话结论

这个编号也混合了不同职责：dev.mjs 和 Vite 负责本地开发；launch-server.sh 负责启动 Application Support 里的4317运行副本；deploy-local-runtime.sh 会覆盖运行副本代码、依赖和构建产物并重启进程。它是本机工程能力，不是中央运行，也不是商品业务能力。

### 当初为什么开发

项目需要三种本机动作：

1. 开发时同时启动 API 与前端；
2. 日常打开已经复制好的4317独立运行副本；
3. 经批准后把当前源码和构建产物复制到运行副本。

这像“开发车间、电源开关和搬运车”被登记在同一张卡里。它们都与运行有关，但危险程度完全不同。

### 表面看起来与实际能力

| 部分 | 实际能做 | 实际不能做 |
|---|---|---|
| scripts/dev.mjs + vite.config.js | 启动本地 API 与 Vite，代理到4319 | 不能证明4317正式副本、不能提供中央服务 |
| launch-server.sh | 校验运行副本 Node 和候选 v2 后启动4317 | 不能更新代码、不能证明业务闭环 |
| deploy-local-runtime.sh | rsync/cp 依赖、server、lib、schema、dist，并强制重启 LaunchAgent | 没有完整回滚；不能自动判断脏工作树是否可部署；不能代替主人上线授权 |

### 输入 → 内部处理 → 输出

| 输入 | 内部处理 | 输出 |
|---|---|---|
| 主源码与 node_modules | 启动开发 API 和 Vite | 本地开发页面 |
| Application Support 运行目录、Node、候选 JSON | 校验并 exec server.mjs | 4317进程 |
| 主源码、依赖、schema、dist | rsync --delete、复制并 kickstart | 被覆盖和重启的运行副本 |

### 谁依赖它，它依赖谁

- package.json 的 dev 调用 scripts/dev.mjs；start 直接调用 server.mjs。
- launch-server.sh 被本机 LaunchAgent 或人工启动使用。
- deploy-local-runtime.sh 只能由人工明确执行，不是 package 默认命令。
- 它依赖本机固定 Application Support 路径、Node、LaunchAgent、dist 和依赖。
- A→E 业务模块不应该直接依赖这些脚本。

### 孤立程度

**启动部分仍是当前本机运行基础；覆盖部署部分是人工高副作用工具。**
它不是孤儿，但也不是“已验证部署系统”。

### 与当前架构的关系

- A→E：仅提供本机承载环境，不推进阶段。
- Multi-user Central Runtime：当前固定本机路径、单进程和4317只能算本地开发适配器。
- 全店经营工作台：4317是旧独立运行副本，不等于当前主源码。
- 全店能力地图：可显示运行边界和版本差异，不能提供“一键部署”或改变真实接线。

### 与其他待归位能力的关系

- 与9.5可能是发布前后关系，但当前 deploy 脚本直接复制主源码，不读取9.5阶段包。
- 与9.10关系明显：当前主源码有地图 API，而冻结运行副本对该 API 返回404，说明运行副本落后。
- 与9.11风险相似：二者都能监听本机端口，但正式启动链只指向 server.mjs。

### 未来三种处理的主要风险

- 继续使用：需要增加明确源码基线、回滚点和部署后独立回读。
- 统一重做：长期更清楚，但会涉及运行目录迁移和回滚设计。
- 退役本机副本：在中央运行尚未实现前会失去当前可用入口。

### 调查建议

保留“开发启动”和“受控部署”两个概念，但以后应拆开登记。任何运行副本覆盖都必须等主人给出精确上线授权，本轮未执行。

## 9.7 Ozon D/E多套候选实现

**所属小组：戊｜Ozon D/E候选与诊断**

### 一句话结论

仓库里确实有能准备 Ozon 写入请求、调用注入式 Seller API、写库存、比对回读和生成记录的代码，但它们处在不同层，有的互补、有的重叠。当前 server 主要只接了“准备度展示”、OSS素材传输和由调用方提交观察值的 E 合同，没有一条正式 Seller API 写入→独立回读主线。

### 当初为什么开发

D/E需要拆开解决许多问题：

- 生产授权怎样变成不可变执行请求；
- Ozon商品导入和库存接口怎样调用；
- 最终图片怎样变成稳定 HTTPS 地址；
- 写入结果怎样归一化；
- 结果未知时怎样停止；
- E怎样从新客户端重新读取并比对；
- 上架后经营指标怎样判断。

这些零件像“装箱单、卡车、签收单、复核员和经营报表”。它们不都是同一岗位。

### 9.7登记范围内四套能力

| 代码 | 实际能做 | 当前调用 | 不能证明 |
|---|---|---|---|
| ozon-seller-api-de-adapter.mjs | 检查店铺/仓库/协议能力；解析最终图片；在注入 requestJson 后可导入商品、写库存并读五类端点 | 领域准备函数用其素材解析；完整 adapter factory 未接 server | 真实凭据、当前协议、正式店铺写入与独立E |
| ozon-production-strategy.mjs | 根据平台和素材位置选择“纯API”或一次人工媒体交接策略 | production-plan.mjs 当前导入 | 不执行API，不产生平台回执 |
| draft-production-execution.mjs | 校验计划/授权/前检，用注入 adapter 创建一个草稿并独立比对 | d-e-software-closure 引用记录合同；完整执行主要在测试 | 不是当前 server 生产路由 |
| post-launch-observation.mjs | 根据访客、加购、订单阈值做经营观察 | UserInspector.jsx 当前导入显示 | 不采集平台数据；不是D/E连接器；E后优化职责尚未决定 |

| ProductionAuthorization、ProductionPlan、写前检查、适配器能力 | 校验 revision、店铺、币种、字段、素材和一次性执行范围 | 可执行请求或明确 gaps |
| 注入的 Seller API 客户端 | 商品导入、任务读取、库存100写入 | 归一化写入回执或 unknown_outcome |

# 六、8组疑似重复能力逐组调查

## 先说明“疑似重复”是什么意思

同一组里的代码不一定应该二选一。出现疑似重复通常有四种原因：

1. 两套代码真的都在做同一个动作；
2. 一套负责计划，一套负责执行，名字相似但互补；
3. 一套是旧兼容，一套是新版目标；
4. 一套只是模拟、测试或诊断，表面输出与正式能力相似。

下面每组都不指定 currentPrimary，只说明真实重叠、互补、冲突和证据缺口。

## 10.1 Ozon D/E候选实现比较组

**所属模块：跨 D 与 E；另含 D前素材传输和E后经营观察。**
**交叉引用：9.7、9.13。**

### 为什么看起来重复

七个成员都出现“生产”“执行”“Seller API”“回读”“ProductionRecord”或“E验证”等词。只看文件名，像有七套上架系统；深入代码后，真正高重叠的是四套写入/执行候选，另外三套分别是计划策略、素材传输和结果比对。

### 七套代码逐项说明

#### 1. d-e-software-closure.mjs：D/E领域总合同

- 原本解决：把授权、计划、前检和适配器能力组合成一次不可重放的 D 动作，并规定 unknown_outcome 与 E复核。
- 表面像：一条完整 D→E。
- 实际能做：准备请求、创建 attempt、标记 unknown_outcome、通过注入函数执行、生成 ProductionRecord、调用只读函数做 E。
- 不能做：自己不持久化；没有凭据；不创建真实网络客户端；server没有正式执行路由。
- 输入→处理→输出：授权/计划/前检/能力 → 严格校验与执行状态机 → 可执行请求、ProductionRecord或E结果。
- 当前依赖：d-e-software-integration 用它生成准备度；完整执行主要由测试调用。
- 状态：部分可达，不是完整生产能力。

#### 2. ozon-seller-api-production-adapter.mjs：单独的商品导入适配器

- 原本解决：把项目生产请求翻译成 Ozon商品导入请求，并把返回归一化。
- 表面像：正式 Ozon D。
- 实际能做：构造 import payload；注入 requestJson 后调用候选API。
- 不能做：不拥有授权、持久化意图和完整 E；server没有正式调用 factory。
- 输入→处理→输出：项目字段＋注入客户端 → 转换成 Ozon请求 → 导入任务回执。
- 当前依赖：d-e-software-closure 用其 buildOzonSellerImportRequest；factory主要测试可达。
- 状态：请求构造被复用，完整适配器游离。

#### 3. ozon-seller-api-de-adapter.mjs：写入与回读合并适配器

- 原本解决：在一处描述店铺、仓库、素材、商品导入、库存写入和五端点独立回读。
- 表面像：另一条完整 D→E。
- 实际能做：检查能力；解析 stable HTTPS素材；注入客户端后导入商品、查任务、写库存100；用新adapter读取五端点。
- 不能做：没有server正式执行入口；能力证据由调用者提供；没有中央job和授权记录。
- 输入→处理→输出：执行请求＋能力合同＋requestJson → 写入与读取 → 归一化结果。
- 当前依赖：d-e-software-closure 使用 resolveFinalUploads；完整 factory主要测试可达。
- 状态：部分被领域层复用，完整执行隔离。

#### 4. ozon-production-strategy.mjs：计划时的路线选择

- 原本解决：判断最终素材已经是远程URL，还是需要一次本机媒体交接。
- 表面像：Ozon生产执行器。
- 实际能做：生成和校验策略对象；production-plan.mjs 当前调用。
- 不能做：不访问API、不上传图片、不写商品、不回读。
- 输入→处理→输出：平台＋finalUploads → 选择策略 → production strategy。
- 状态：当前领域调用存在，但它与adapter是上下游，不是同一能力。

#### 5. draft-production-execution.mjs：通用单草稿执行器

- 原本解决：只创建一个用于审核/验证的草稿，防止顺便扩展库存、发布、广告等范围。
- 表面像：正式 D执行。
- 实际能做：校验授权与计划；调用注入createPlatformDraft；保存ProductionRecord形状；要求独立readback匹配。
- 不能做：默认不承担完整库存、激活和正式发布；没有server生产入口。
- 输入→处理→输出：草稿生产计划＋adapter → 单次草稿创建和比对 → ProductionRecord。
- 当前依赖：d-e-software-closure复用其记录校验；主要测试可达。
- 状态：高重叠执行候选，但产品范围比组合adapter窄。

#### 6. aliyun-oss-d-asset-integration.mjs：最终素材传输

- 原本解决：把主人确认的finalUploads变成平台可接受的稳定HTTPS地址。
- 表面像：D写入的一部分，所以容易和Ozon adapter混在一起。
- 实际能做：创建并持久化一次素材意图；上传到OSS；记录unknown_outcome；服务重启后禁止自动重放。
- 不能做：不建商品、不写价格库存、不提交审核、不做E。
- 输入→处理→输出：授权＋最终素材＋一次性意图 → OSS传输 → 已验证稳定地址或unknown_outcome。
- 当前依赖：server有 /lifecycle/d/asset-transport 路由；D/E准备度卡间接显示。
- 状态：当前服务有接缝，是独立前置能力，不应参与“选哪套Ozon写入”的二选一。

#### 7. e-stage-readback.mjs：E结果比对合同

- 原本解决：把“平台观察到的结果”与ProductionRecord或外部商品身份严格比对。
- 表面像：完整平台回读。
- 实际能做：校验观察和身份，生成EVerificationRecord。
- 不能做：不访问平台；当前server路由的verifiedObservation仍由调用方提交。
- 输入→处理→输出：生产/外部记录＋已验证观察 → 身份与字段比对 → EVerificationRecord。
- 当前依赖：server E路由和d-e-software-closure。
- 状态：比对合同可达，正式provider缺失。

### 重复到什么程度

| 关系 | 判断 |

| d-e-software-closure 与两个 Seller API adapter | 互补中有重叠：前者应管领域状态，后者应管平台协议；但请求构造和回读归一化边界尚未完全收敛 |

- 一套路径以“只创建验证草稿”为安全范围，另一套候选包含库存100写入；正式 D范围尚未通过真实平台验收。

### 选择的利弊

## 10.5 手工回读与正式独立回读比较组

**所属模块：E为主；另跨历史人工支路和E后经营观察。**
**交叉引用：9.7、9.9、9.13。**

### 为什么看起来重复

四套成员都能生成“已上架”“已验证”“观察结论”一类结果。真正差别不在结果名字，而在“谁取得平台事实”：

- 人工填写；
- 人工提供经营指标；
- 领域合同只负责比对；
- 正式provider候选真正去平台读取。

### 四套能力逐项说明

#### workflow.mjs：旧人工上架与回读校验

- 原本解决：没有正式连接器时，让人把商品ID、链接、审核和销售状态写回本地。
- 实际能做：校验输入形状与时间，生成manual_fallback或automatic_readback形状的本地记录。
- 不能做：不访问平台，不能证明信息没有填错。
- 输入→处理→输出：人工listing/readback → 格式校验 → 本地旧上架记录。
- 调用：server旧API、src/api.js和当前UserInspector。
- 状态：仍在用的历史人工支路。

#### post-launch-observation.mjs：上架后指标判断

- 原本解决：根据访客、加购、订单判断继续观察、流量不足或商品卡问题。
- 实际能做：纯阈值计算。
- 不能做：不采集指标、不验证平台商品、不属于E独立回读。
- 输入→处理→输出：调用方提供指标 → 阈值规则 → 经营提示。
- 调用：当前UserInspector直接导入，注册表写“未接UI”已经落后。
- 状态：当前UI使用的纯规则；是否长期属于本项目尚未决定。

#### e-stage-readback.mjs：正式E比对合同

- 原本解决：严格区分系统创建商品和外部发现商品，绑定ProductionRecord/ExternalListingRecord后生成EVerificationRecord。
- 实际能做：身份、价格、素材、库存和状态比对。
- 不能做：不主动访问平台。
- 输入→处理→输出：生产记录＋verifiedObservation → 严格比对 → EVerificationRecord。
- 调用：server当前E路由和D/E领域组合。
- 状态：领域合同已接，provider未接。

#### ozon-seller-api-de-adapter.mjs：候选正式provider

- 原本解决：用新的store-isolated adapter读取Ozon属性、商品、价格、库存和失败状态。
- 实际能做：注入真实requestJson后独立读取并归一化。
- 不能做：当前无server正式provider入口；能力证据和授权尚未绑定中央job。
- 输入→处理→输出：店铺/商品身份＋只读客户端 → 多端点读取 → 平台观察。
- 调用：测试和D/E候选代码。
- 状态：外部只读候选，尚未接正式E。

### 重复到什么程度

| 关系 | 判断 |
|---|---|
| workflow 与 e-stage | 输出语义高重叠，证据来源冲突；前者人工，后者要求已验证观察 |
| post-launch 与 E | 只在“都发生于上架后”上相似；一个看经营表现，一个核对平台写入 |

- 人工按钮能把本地状态变成已上架，容易被UI误解为平台完成。

**交叉引用：9.8、9.9。**

### 三套成员逐项说明

#### legacy-candidate-adapter.mjs：旧数据翻译员

- 原本解决：把旧扁平候选映射到新版对象而不猜字段。
- 输入→处理→输出：旧候选 → 保守字段映射 → read-only OpportunityPackage。
- 调用：server、入口预览、FireTrain旧路径。
- 状态：当前在用的兼容桥。

#### real-lifecycle-entry-preview.mjs：入口检查员

- 原本解决：告诉主人一条旧候选离新版A入口还缺什么。
- 输入→处理→输出：候选和适配结果 → readiness/gaps判断 → UI预览。
- 调用：server候选公共投影、CandidateDetail。
- 状态：当前UI在用。

#### product-lifecycle-schema.mjs：新版正式合同

- 原本解决：规定OpportunityPackage、SkuLifecyclePackage、ProfitModel和后续对象的严格结构与校验。
- 输入→处理→输出：规范对象 → schema/domain校验和版本追加 → 可供A→E使用的稳定对象。
- 调用：众多正式领域模块。
- 状态：正式底座；它本身不采集、不确认、不推进。

### 为什么看起来重复

三者都能产出或展示“生命周期对象”，但分工是：

- adapter负责翻译；
- preview负责解释缺口；
- schema负责规定什么才算合法。

它们不是三套入口，更像“翻译员、门卫和法律文本”。

### 实际重叠、互补与冲突

- adapter与schema：互补；adapter输出必须符合schema。
- preview与adapter：互补；preview消费适配结果。
- 主要冲突：adapter基于旧字段，只能read-only；不能把适配成功解释为满足A合同。
- server某条销售采集路径会保存兼容机会包，说明它不只是纯页面预览，必须持续标出legacySource.readOnly。

### 四层事实

- 文件存在：三套都存在。
- 存在调用：三套都有当前调用。
- 运行副本：冻结快照只说明部分文件存在，不证明当前页面和保存路径。
- 真实业务验证：适配器测试通过不代表旧候选完成A。

### 调查建议

当前应三者并存而不是选一个currentPrimary。未来要决定的是兼容桥何时退出，而不是从三者中选胜者。任何迁移必须保留unknown和来源。

## 10.8 两套B利润与C1交接组合比较组

**所属模块：B为主，跨 B→C1交接。**
**交叉引用：9.14。**

### 先纠正注册表中的事实

当前组名和note写“二者都能计算B并产生C1交接”，实际不成立：

- real-a-b-c1-flow.mjs 确实计算B并创建唯一C1 handoff；
- product-lifecycle-b-flow.mjs 只创建SKU包和计算B，c1ProductPlan保持null，没有handoff函数。

因此本组真正比较的是“两套SKU包/B利润实现”，只有第一套覆盖B→C1。

### 两套能力逐项说明

#### real-a-b-c1-flow.mjs：当前server可达组合

- 原本解决：主人在一张A卡确认后，服务端使用冻结证据做B；通过时原子地产生且只产生一次C1交接。
- 实际能做：确认/淘汰；SKU包；利润；证据缺口；幂等；C1ProductPlan；handoff；负责人切换。
- 不能做：外部证据不齐时不能给正式利润；本函数本身不访问平台。
- 输入→处理→输出：候选＋主人提交＋证据包 → 校验和B → 生命周期结果＋唯一C1 handoff。
- 当前调用：real-a-b-evidence-orchestration 和 server。
- 状态：当前主源码运行入口，但不代表运行副本/真实业务已验收。

#### product-lifecycle-b-flow.mjs：测试可达B实验台

- 原本解决：从规范OpportunityPackage和供应确认创建SKU包，再独立验证B利润模型。
- 实际能做：createSkuLifecyclePackage、runBProfitModel、追加版本、fail-fast、零网络。
- 不能做：没有C1计划、handoff、负责人切换、持久化和server入口。
- 输入→处理→输出：规范A对象＋确认＋费用/汇率 → B计算 → SKU包＋ProfitModel。
- 当前调用：仅single-sku-b-flow测试。
- 状态：测试候选。

### 为什么看起来重复

两者都引用生命周期Schema、市场样本和定价规则，也都生成ProfitModel。测试里的结果结构很像。差异在于：

- 第一套从UI候选和确认卡进入，并负责原子交接；
- 第二套从已准备好的规范对象进入，只验证B领域计算。

- 真实业务验证：本轮没有真实SKU业务回执；第二套5项纯领域测试通过。
