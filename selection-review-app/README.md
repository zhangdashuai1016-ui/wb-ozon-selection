# 今日选品评审台

这是本地只读选品协作网页。它不会连接店铺写接口，也不会创建、发布或修改商品、库存、价格或广告。

## 使用

系统登录后会由 macOS 自动启动后台服务。重新打开浏览器时，直接打开
`今日选品评审台.webloc`，或双击 `启动今日选品评审台.command`。页面地址固定为：

`http://127.0.0.1:4317/`

后台服务只监听本机地址，不对局域网或互联网开放；异常退出后系统会自动拉起。
运行日志位于 `~/Library/Application Support/今日选品评审台/logs/`。

### 安装商品只读采集器（本机一次）

1. 在Chrome打开 `chrome://extensions/`，开启右上角“开发者模式”。
2. 点击“加载已解压的扩展程序”，选择本项目的 `selection-review-app/extension/1688-capture`。
3. 保留评审台地址为 `http://127.0.0.1:4317/`；安装或更新扩展后刷新评审台页面。

该扩展只在主人从评审台点击后工作。当前支持两种互不混用的单商品只读采集：A阶段读取1688精确供应SKU；A阶段读取Ozon当前商品页面已经加载的页面组件，提取标题、当前直接价格、图片、属性和卖家身份证据。评审台同一时刻只允许一个商品采集会话，另一个商品不会排队、不会自动重试，也不会改变业务状态。扩展只访问1688详情页、Ozon商品页和本机4317，不申请Cookie权限、不调用AI或第三方服务，也不执行下单、采购或店铺写入。缺失字段保持“未取得”，不会填库存999、默认包装、最低价或猜测卖家身份。登录、验证、超时、商品ID不一致或直接价格缺失时立即停止，技术失败不会改变商品业务状态。

页面右上角“添加我找到的商品”只要求目标店铺和商品链接。保存后商品直接进入“Codex处理中”，不要求用户重复判断。

## 处理流程

评审台把选品拆成三段，禁止跨阶段混用淘汰理由：

1. **A 方向与供应方案**：检查目标平台市场、跨境商品份额、市场体量/趋势和初步利润空间；再采集精确1688链接、供应SKU、商品价格、国内运费、实际采购成本、重量和尺寸，由主人确认供应方案。销售样本优先顺序为中国跨境、其他跨境、证据完整的身份未确认样本、本土背景价；中国跨境优先但不唯一。`sellerType=unknown` 只要商品可比、价格清晰、页面可追溯且证据有效，就可参与主要价格带并推动A进入B；`local_ru` 不能单独决定中国跨境采购上限或利润通过。
2. **B 具体SKU利润核算**：只读取A阶段冻结的销售快照、主人确认供应SKU、费用证据、物流证据和汇率，输出建议售价、单件利润与利润率；不重新访问Ozon/WB/1688。
3. **C1/C2 上架方案准备**：B通过后自动进入C1，由上架任务继承冻结数据完成事实、合规、Schema和SEO；C2只接收主人确认的最终素材。C1+C2完成后才展示生产授权卡。

页面右上角的“第2A模拟验收”是与真实52条候选完全隔离的纯模拟闭环：主人在一张A阶段确认卡里完成方向、供应链接、具体SKU、商品价、国内运费、实际采购成本、重量和尺寸确认；一次提交后，B只读取冻结快照自动计算并在达标时幂等进入C1。模拟接口不保存候选、不派发真实任务，也不访问Ozon、WB、1688或拼多多。

四条状态线不绑定某个测试商品ID：存在 `OpportunityPackage` 时显示方向阶段状态，存在 `SkuLifecyclePackage` 时优先显示SKU生命周期状态。历史只读适配产生的 `unknown` 原样显示，禁止为了页面好看推断成A、通过或完成。

旧的 `awaiting_user_start`、旧“开始上架准备”和旧1688 C阶段采集状态仅为历史兼容读取。新版生命周期商品调用旧入口会明确拒绝且不改变状态；已上架商品的1688证据补录仍保留为独立只读恢复能力，但不能创建C阶段派发。

- “待你确认”只放 Codex 选品。用户点“不行”后立即淘汰；点“可做”或“待确认”后自动进入 Codex 审核。
- “待你确认”每张候选卡都显示“含国内邮费采购价上限”。只有卖家收入、当前真实佣金和最终包装国际运费可追溯时才显示反算金额；证据不足时明确显示“采购上限未验证”和缺口，不生成猜测金额。
- “Codex处理中”不要求用户操作。用户提交的商品和已认可方向的商品都在这里自动核算市场、佣金、物流和利润。
- “需你补资料”只显示 Codex 无法自行取得的具体字段；保存后自动重新排队。
- 用户填写的“采购价”固定表示货价＋国内运费的到手总成本。系统不再拆分、重复询问国内运费；已经填写的采购价、重量、尺寸和精确链接也不得再次索取。若多规格页面与现有价格存在冲突，最多只确认一次该价格对应的目标SKU/套装。
- B阶段利润通过后，服务端自动创建C1并把唯一负责人切换给上架任务，选品任务立即停止；不再要求主人点击“开始上架准备”。
- 数据实时写入项目内的 `data/candidates.json` 共享入口，不是浏览器临时数据。
- 为避开 macOS 对“文稿”目录后台进程的隐私限制，该入口链接到
  `~/Library/Application Support/今日选品评审台/data/candidates.json`；Codex与网页读写的是同一份文件。
- 自动领取、定时重试和巡检目前暂停。候选处理只在总控明确指令后启动；不得用后台循环重试代替业务结论。
- 防空跑门禁：只有同时具备 `runId + startedAt + currentStep + lastProgressAt` 才显示“实际运行”；同一轮、同一证据层、同一目标只允许一次读取。一次有证据的技术失败立即停止并等待总控；15分钟没有新证据或真实步骤变化也会停止，只生成一条去重后的总控提醒，不再自动排队。
- 健康检查、队列未变化和重复证据不算业务进展，不得产生用户可见任务消息。
- 页面每3秒刷新共享数据；Codex写回后无需重新录入。
- 蛋蛋鼠主动研究按“Seerfar市场先行”执行：节日/趋势只是入口；跨境商品份额须≥40%，并先用目标Ozon市场价、当前佣金和可行包装物流建立正采购空间，再在正利润方向内找具体SKU。无正采购空间的方向不得进入用户待确认。
- Miska未来一周只审核用户主动提交品，不主动扩散或自动新增。至少积累5个完整、独立、利润通过并进入待上架的结构样本（同商品颜色/尺寸变体只算1个），且能归纳至少1个可检验共同经济结构后，才向总控提交1份共同点假设和最多3条Seerfar验证方向；未经确认不得新增。

## 严格门槛

只有同时满足以下条件，服务端才接受“审核通过”：

1. 非电，或带电商品已核实目标平台与实际物流线路均允许；
2. 合规与授权清楚；
3. 市场证据当前、可追溯且与目标SKU具有合理可比性，足以支持建议成交价；样本数量少只降低判断可信度，不自动阻断，完全没有可比价格或样本冲突到无法形成合理价格区间时才停止补证据；
4. 真实打包重量与尺寸完整；
5. 当前真实佣金、物流线路和完整利润复算通过；默认自然流量、广告成本为0，有真实投放计划时另算；
6. 蛋蛋鼠、Miska 和 WB 的完整复算统一要求：单件利润至少20 RMB，或利润率至少15%，满足任一项即可。

20%/25%/30%是促销折扣空间，不是广告成本。若市场参照是折后成交价，利润直接从该成交价计算；建议标价分别按“折后成交价÷(1−促销率)”反推，禁止再从成交价扣一次促销率。若输入是标价，则先换算预期折后成交价再计算利润。已有候选的旧二次扣费结果保留为历史但不再作为当前结论，不自动重算、不静默覆盖。

当前精确佣金暂时取不到时，只有用户针对当前SKU明确允许，B阶段才可使用清楚标注的估算佣金形成估算利润结论。估算费率不能写成当前平台事实；C阶段仍须重取当前店铺、类目和销售模式的精确佣金。估算佣金没有经过C阶段精确核验前，不得进入“可上架”。

C1自动开始只授权当前SKU的上架前只读核验，不授权创建商品、上传素材、修改价格库存或发布。评审台把A/B冻结数据包交给上架任务，不重复索取。C1+C2通过后仍须展示并取得平台、店铺、SKU、价格、默认库存100、素材、发布范围和排除项的精确确认。

候选进入且资料足够时自动触发一次A/B处理。任一技术失败立即停止当前SKU，记录失败层、原因、是否写入和最小恢复动作；系统不自动重试。用户可在主界面留言并点击“按我的建议重试一次”创建新的单SKU执行。第一版不提供批量按钮。

一次性任务的业务结果通过 Codex App Server `turn/start` 的 `outputSchema` 结构化返回，由评审台服务校验后写入共享数据；执行任务不反向连接 `127.0.0.1:4317`，因此本地端口隔离不能再造成“任务已回复但结果无法回传”。C阶段派发会按OpenAI官方协议同时附加 `$skill-name` 文本和 `skill` 输入项，并在派发记录中保存实际附加的Skill；缺少必需Skill时停止本次派发，不使用普通提示词兜底。重试快照只补当前缺口，不从头重复核算。

佣金、官方汇率、物流资费、Schema和带电运输规则可以按准确适用范围与有效时间形成共享证据包；商品自身重量尺寸、电池与包装属性仍逐SKU确认。三店合计每日目标为10个B阶段利润通过商品，页面另行显示C完成和真正可上架数量。

“待上架”不等于“已经发布”；评审台本身不构成店铺生产授权。Ozon 与 WB 是相互独立的平台生命周期：目标平台是 Ozon 时，不得因尚未完成 WB 判断而阻止进入 C1；目标平台是 WB 时，也不得套用 Ozon 的市场、佣金或物流结论。若同一商品同时评估两个平台，分别保存各自的销售快照、费用证据和利润结论；任一平台达到单件利润20 RMB或利润率15%的统一门槛即可在该平台流程内继续，不能由另一平台代替判断。

## 上架任务自动回写

“待上架”的主流程不是用户手动点完成。上架任务在平台创建完成并重新读取当前状态后，调用：

`POST /api/candidates/{candidateId}/listing-readback`

请求必须包含当前 `dataRevision`，以及以下真实回读字段：

- `platform`：`ozon` 或 `wb`
- `store`：`dandanshu`、`miska` 或 `wb`
- `productId`、`merchantSku`
- `productUrl`（平台能够取得前台链接时填写）
- `confirmedAt`、`moderationStatus`、`saleStatus`
- `readback.sourceType="real"`
- `readback.source="seller_api"` 或 `seller_portal`
- `readback.checkedAt` 与 `readback.evidenceRef`

服务端只接受24小时内的 Seller API/卖家后台真实回读，并校验候选仍处于待上架、负责人为上架任务、平台与店铺一致、数据修订号没有过期。通过后自动保存完整上架记录、完成交接并移入“已上架”。重复发送同一平台商品回读是幂等的；不同商品不得覆盖。

页面中的“无法自动回读？手动标记”只是兜底。它会明确记录为 `manual_fallback`，不能伪装成自动回读，也不能依据旧聊天记录自动迁移。

“双方记录与留言”提供两种动作：“发送并交给Codex”会把非终态候选的问题标为待回复并重新送审；“仅记录”只保留历史，不触发重审。待上架和已上架商品由上架任务负责，不允许留言把同一SKU重新送回选品队列。Codex回复会关联原留言并显示“已回复”。

## 开发检查

纯测试不启动 HTTP 服务；API 集成测试会启动临时服务，两者分别运行：

```bash
node scripts/run-ci-tests.mjs
node node_modules/vite/bin/vite.js build
node --check server.mjs
```

GitHub 的 `Isolated API integration tests` 检查运行其余 14 个 API 测试文件。它只使用合成候选、临时文件和假派发程序，在无外网、非 root、代码只读的独立容器内运行；仅允许容器内回环 HTTP，不加载凭据或调用真实业务服务。`node scripts/run-ci-api-tests.mjs` 只接受该隔离环境，不是本机启动入口。服务退出失败或超时会使测试失败。

派发所需能力文件可通过 `SELECTION_REVIEW_DISPATCH_SKILLS_DIR` 指定绝对目录；每项仍使用固定的 `<能力名称>/SKILL.md` 路径，并在派发前检查文件存在。未设置时保留原默认目录。API 测试将此目录指向临时合成文件，不读取个人能力目录。
