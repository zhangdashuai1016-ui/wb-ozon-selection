### 为什么归档不逐字节复制授权正文

实测撞出来的，不是体积偏好：候选聚合提交时会走 `assertSafeBusinessMutationCandidate → normalizeProductionEntities`，把授权和生产计划抽成独立实体记录；副本放到新路径上归一化认不出，会直接拒绝整笔事务。因此授权正文留在 `document.productionEntityRecords`（不删），归档只留 `entityId` + 指纹；`dAssetTransport` 内嵌的生产计划同理换成 `production-plan-archive-ref-v1` 引用——**这一换让单条归档从约 187 KB 降到 64 KB 以内**。

归档整份**不重跑** `assertNoProductionSecrets`，只扫本动作新造的元数据（`assertNoProductionSecrets` + `assertSafeRuntimeRecord` 两道都过）。重扫会踩密钥扫描器对 `authorizationRef` 这类键名的已知误判，逼着删字段，留底就不再是留底；而被留底的记录已各自过了自己那道门。

## 4. 按钮互斥规则

| 状态 | 亮哪个 |
|---|---|
| `dProductionRoundDispatchable().dispatchable === true` | 只亮「再派一轮生产作业」 |
| 被 `DOWNSTREAM_EXISTS`、`REVISION_MOVED` 或 `ROUND_LIMIT` 挡住，且放行证据齐全 | 只亮「作废本轮授权、退回等我确认」 |
| 其余（`ROUND_MAY_HAVE_SENT`、`ROUND_NOT_STOPPED`、`NO_ROUND`、证据不齐） | 两个都不亮，各显阻断原因 |

**可作废的阻断集合固定为 `{DOWNSTREAM_EXISTS, REVISION_MOVED, ROUND_LIMIT}`**，三者语义一致：一个请求都没发出去，只是这条路走不下去。集合写在 `production-authorization-rollback.mjs` 的常量里，**后端以此集合 + 放行证据为准，前端只负责显示**。

「继续已保存任务」照旧只在 `queued / attempt 0` 时亮，与上述两者无关。

**安全关键**：`ROUND_MAY_HAVE_SENT` 表示上一轮可能已经把请求发出去、终态未知，此时作废按钮必须不亮，**且后端即使收到请求也必须拒绝**（不依赖前端不显示）。已有反向断言覆盖。

`ROUND_LIMIT`（轮次用尽但无下游记录、修订也没动）由讲解会话 2026-09-23 定为放行作废，已按此实现并有用例。背心命中的是 `DOWNSTREAM_EXISTS`。
