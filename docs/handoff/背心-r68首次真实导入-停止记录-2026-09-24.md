### 3.1 本文初稿两处推断作废（更正留痕）

初稿曾据 `platformContinuation.policy = null` 推断「loader 返回 null，故 :651 不适用」，并据手动回放推断「守卫块命中 `DE_JOB_SCOPE_D_ALREADY_ADVANCED`」。**两条都不成立**，按源码逐条核实如下：

1. `lib/d-e-software-closure.mjs`：导入被接受时构造的 `platformContinuation` **一律写死 `policy: null, queryCount: 0`**，与 loader 返回什么无关。**该字段不能作为"没有策略"的证据。**
2. `lib/d-e-software-job-admission.mjs:142-143`：`assertDProductionJobScope` **只在 `phase === 'enqueue_current'` 时被调用**，其余 phase 走 `assertCurrentDJobExecutionCursor`；而 settle 走的是 `external_request`。初稿回放用的是 `continue_current` / `enqueue_current`，**都不是现场那一段代码**，结论不能当证据。

这也解释了 r68 第 3、4 条合成测试为何能走到 `waiting_platform`：同一段守卫在测试里是过的，**测试与生产唯一的实质差异就是策略的 `expiresAt`**（测试里注入的是 2099 年）。

## 5. 第二个缺口：策略是"配了、匹配得上、但已过期"，不是"没配"

`normalizeDPlatformObservationConfiguration` 不检查 `expiresAt`，过期条目照样留在 `policies` 里；`createDPlatformObservationPolicyResolver` 只按 candidateId / skuPackageId / productionBindingId / productionConfigurationVersion 四项匹配，四项与 round2 作业的 `scopeBinding` 全等，**loader 返回的就是那条过期策略**。

修法因此不是"补配置"，而是**换版本号 + 把过期检查前移**。

## 5.1 第三个缺口：停止记录不带判定细节

停止只落盘 `stopReason = context_changed`，**不记触发它的是哪一行、比较的两个值是什么**。本次两人各查约一小时才定位，期间还产生了第 3.1 节那两条错误推断。r69 须把触发条件（判定点、两个被比较的值）写进 stop payload。

## 5.2 软件有没有现成的恢复入口：**没有**

- `isReconciledDERequest`（`d-e-software-job-results.mjs:20`）要求 `status='unknown_outcome'`、`externalRequestState='unknown_outcome'`、`failureClass ∈ [service_restart_after_external_request, lease_expired_after_external_request]`、`resultEnvelope=null`。本条五项全不匹配。
- `resumeInventory`（`d-e-runtime-services.mjs:283`）是**观察作业确认之后**的续写入口，且首先读 `state.platformContinuation.policy.expiresAt` —— 该字段被固定写成 null，进不去。
- 排观察作业（`d-e-software-integration.mjs:686`）要求策略非 null，且要从一个未停止的 D 作业上排。本条已 `failed` 且 `continuationBlocked = true`。

**结论：对「已被平台接受、停在 `d-initial-import-context-changed`」的执行，软件没有任何现成入口能对账后重建观察、继续写库存。**按 AGENTS 9.1，属 unknown_outcome 对账/恢复那条**独立授权面**，须主人单独授权，不得复用原生产授权自动跑。

### 5.3 但底下压着一个真问题：续写后一旦失败，失败本身落不了盘

用**真实可能发生**的条件复现：平台回读价 99 ≠ 授权价 63.85。

```
D_PRODUCTION_PREPARATION_JOB_CONFLICT
  at assertDProductionPreparation (d-production-preparation-contract.mjs:66)
  at readDProductionJobTerminal (d-e-software-job-results.mjs:187)
  at settleDProductionSoftwareJobInDocument (software-job-contract.mjs:1199)
```

原因是结构性的、必然的：

```
job.leaseId  : lease:d-inventory:694f598f-…   ← claimDRemainingInventory 新铸
prep.leaseId : lease:de:9a6a45ae-…            ← 当初导入那次 claim 的
```

前缀由构造决定（`lease:d-inventory:*` vs `lease:de:*`），**永不相等**；
而 66 行要求 `['jobId','candidateId','skuPackageId','revision','workerId','leaseId']` 逐项相等。

**分界**：187 行在 `if (state.status !== "succeeded")` 块内（160 行）。
所以**成功档不走到这里**（因此 CI 全绿、5.1 也跑通了），**失败/unknown 档必炸**，且炸在结算事务里。

后果比报错本身重。崩完落盘剩下：

```
D作业 : waiting_platform / in_flight / failureClass null   ← 没有失败分类
执行  : in_flight，attempt.failure null，attempt.reason null
platformWrites : unknown                                  ← 可库存其实已经写进去了
生产记录 : null
观察作业 : 3 条全 completed                                ← 泵不会再跑
真实原因（价格不符）: 落盘里找不到
```

事务回滚，**软件没法把这次失败记成失败**，租约还攥着，作业卡死在 `waiting_platform`。
对照 AGENTS 第 0 节「已知失败必须由软件分类、持久化并安全停止」「不得导致状态丢失、
**半套写入**或**无法判断卡点**」——同时踩中后两条。**形状与背心本次原始事故一致：
作业卡住、没有诊断。**

### 5.4 待定（已报同行，未动代码）

倾向改法：66 行的 job 交叉校验里**去掉 `workerId`/`leaseId` 两项**，其余保持严格。
理由：准备证据记的是「当初是谁、用哪个租约做的前检」，这是历史事实，本来就该不可变
（`workerId`/`leaseId` 都在 `immutableFields` 里、参与 `preparationId` 指纹，改字段等于篡改历史）；
错的是拿历史租约去比**当前**租约。当前持有者的绑定另有一处在盯：
`readDProductionJobTerminal:148` 的 `isDeepStrictEqual(state.softwareJobRef, {...leaseId})`，
而这正是 `resumeDRemainingInventoryInDocument:204` 更新 `softwareJobRef` 的原因。
**两处都要求租约一致，只同步了一处**——更像漏了，不像设计。
